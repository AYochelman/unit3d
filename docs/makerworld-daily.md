# מודלים חדשים מהאוספים — מדריך מלא, מאפס

**מה תקבל בסוף:** מודל שאתה שומר לאוסף במייקרוורלד בערב מחכה לך לאישור
ב-`/admin` למחרת בבוקר. אתה לא עושה כלום — רק מאשר.

**כמה עבודה זה דורש ממך:** התקנה חד-פעמית של כ-20 דקות, פעם אחת בחיים.
אחרי זה זה רץ לבד כל יום.

**מה צריך לדעת מראש:** כלום. המדריך הזה מניח שלא התקנת אף פעם Git, לא יודע
מה זה clone, ולא נכנסת מעולם ל-Task Scheduler. כל שלב כתוב בדיוק כפי שהוא
נראה על המסך.

## קודם — למה זה רץ על המחשב שלך ולא בענן

זאת השאלה הראשונה שכל אחד שואל, ומגיעה לה תשובה ישרה.

הכל **כבר בנוי בענן**. יש ב-GitHub workflow בשם `sync-collections.yml` שרץ
פעמיים ביום, והחיבור שלך למייקרוורלד שמור שם. הוא רץ כל לילה, מדווח
`signedIn: true` — כלומר הוא מחובר בהצלחה — ומיד אחרי זה מדווח `Cloudflare`
על כל שמונת האוספים.

**זאת לא בעיית הרשאות. זאת בעיית כתובת.**

Cloudflare — שירות האבטחה שמייקרוורלד משתמשת בו — מגישה אתגר אבטחה
("Just a moment…") לעמודי האוספים כשהבקשה מגיעה מכתובת של מרכז נתונים.
בדקתי שתי דרכים כאלה: גם את השרתים של GitHub, גם שירות דפדפן מארח בתשלום.
שתיהן נחסמו. **מה שלא נחסם זה חיבור ביתי רגיל** — כלומר המחשב שלך, בבית,
דרך ספק האינטרנט שלך.

לכן הסנכרון עובר לרוץ אצלך. אין דרך עוקפת; זה לא עניין של להתאמץ יותר.

> ה-workflow ב-GitHub נשאר דלוק. הוא לא מזיק, הוא רושם מה קרה, ואם Cloudflare
> תפסיק לחסום כתובות שרתים — הוא יחזור לעבוד לבד והמשימה במחשב תהפוך למיותרת.
> עד אז, המשימה במחשב היא מה שעובד.

## שלב 1 — שתי התוכנות שצריך

צריך שתיים, שתיהן חינם:

- **Git** — מה שמוריד את הפרויקט למחשב ומחזיר אליו שינויים
- **Node.js** — מה שמריץ את הסקריפט של הסנכרון

### הדרך הקלה: שתי פקודות

פותחים **Command Prompt** (בתפריט התחל: להקליד `cmd`, Enter) ומדביקים
שורה אחר שורה:

```
winget install --id Git.Git -e --source winget
winget install --id OpenJS.NodeJS.LTS -e --source winget
```

`winget` מובנה בכל Windows 10 ו-11. הוא מוריד, מתקין, **ומגדיר את ההגדרות
נכון בעצמו** — בלי מסכי מתקין ובלי שום אפשרות לבחור לא נכון. אם הוא מבקש
אישור, לאשר.

**זאת הדרך המומלצת, ולא סתם:** במתקין הידני של Git יש מסך אחד שבו בחירה
שגויה מובילה בדיוק לתקלה שכולם נתקעים בה (מפורט למטה). `winget` לא נותן
לזה לקרות.

### אם `winget` לא מוכר במחשב שלך

אז ידנית:

1. **Node.js** — <https://nodejs.org> · ללחוץ על הכפתור שכתוב עליו **LTS**
2. **Git** — <https://git-scm.com/download/win> · Next על הכל **חוץ ממסך אחד**:
   כשמגיעים למסך שכותרתו **Adjusting your PATH environment** — לבחור את
   **האפשרות האמצעית** (*"Git from the command line and also from 3rd-party
   software"*), ולא את הראשונה.

### 🔧 "מותקן, ועדיין לא עובד" — שלוש התקלות היחידות

כל מי שנתקע, נתקע באחת משלוש האלה. תעבור עליהן לפי הסדר.

#### א. החלון ישן

זאת הסיבה הכי שכיחה, והכי מטעה.

**התסמין:** `'git' is not recognized as an internal or external command`
למרות שההתקנה הסתיימה בהצלחה.

**הסיבה:** חלון Command Prompt שנפתח **לפני** ההתקנה לא מכיר תוכנות
שהותקנו אחריו. הוא קרא את רשימת התוכנות פעם אחת כשנפתח, והיא לא מתעדכנת.

**התיקון:** לסגור את החלון. לפתוח חדש. לנסות שוב.

#### ב. הכותרת אומרת "Select"

**התסמין:** הקלדת פקודה, לחצת Enter, ושום דבר לא קורה. החלון קפוא.

**הסיבה:** זה לא תקוע — זה **מושהה**. אם לוחצים בתוך חלון Command Prompt
עם העכבר, Windows נכנס למצב סימון טקסט ומקפיא את מה שרץ. אפשר לזהות את זה
בכותרת החלון: כתוב שם **Select** לפני השם.

**התיקון:** ללחוץ **Esc**, או Enter. החלון ממשיך מהמקום שבו היה.

#### ג. במתקין נבחרה האפשרות הראשונה

**התסמין:** `git --version` לא עובד, אבל אתה בטוח שהתקנת.

**הסיבה:** במתקין של Git, במסך **Adjusting your PATH environment**, האפשרות
הראשונה — *"Use Git from Git Bash only"* — **לא הופכת את git לזמין
ל-Windows**. מי שלחץ Next על הכל עלול לקבל אותה.

**קודם נבדוק אם הוא בכלל מותקן.** ב-Command Prompt:

```
"C:\Program Files\Git\cmd\git.exe" --version
```

| התשובה | המשמעות | התיקון |
|---|---|---|
| מחזיר מספר גרסה | מותקן, פשוט לא נגיש | להריץ שוב את `winget install --id Git.Git -e --source winget`, או את המתקין ולבחור **באמצע** |
| "The system cannot find the path specified" | לא מותקן באמת | להתקין מחדש |

**דרך עוקפת שעובדת מיד, בלי להתקין שוב:** להקליק ימני על שולחן העבודה או
על תיקייה, ולבחור **Git Bash Here**. זה חלון שמכיר את git תמיד, בלי קשר
לבחירה במתקין. משם אפשר להמשיך לשלב 2 (הפקודות שם מעט שונות — כתוב
בהמשך).

> הסקריפטים של הפרויקט כבר לא תלויים בזה: `sync-daily.bat`
> ו-`first-time-setup.bat` מחפשים את git גם במקומות שהמתקין משתמש בהם, לא
> רק ברשימה הרשמית. גם אם הבחירה במתקין הייתה שגויה — הם יעבדו. אבל עדיף
> לתקן, כי כלים אחרים כן יצפו למצוא אותו שם.

התיקייה הזאת לא עולה ל-GitHub (היא רשומה ב-`.gitignore`). ההתחברות שלך
לא מגיעה אליי ולא עוזבת את המחשב שלך.

אם יום אחד בכל זאת תתנתק — מריצים שוב את אותו קובץ. זה כל התיקון.

## שלב 5 — המשימה היומית

זה השלב היחיד שדורש מילוי טופס. לך לאט, אין כאן שום דבר מסובך.

1. בתפריט התחל להקליד **Task Scheduler** ולפתוח אותו
2. בצד ימין: **Create Task…**
   > ⚠️ **לא** "Create Basic Task" — זה אשף מקוצר שחסר בו השדה שאנחנו צריכים
3. לשונית **General**:
   - **Name:** `Unit3D MakerWorld Sync`
   - לסמן ✅ **Run whether user is logged on or not**
4. לשונית **Triggers** → **New…**:
   - **Begin the task:** `On a schedule`
   - **Daily**, שעה **07:45**
   - **OK**
5. לשונית **Actions** → **New…**:
   - **Action:** `Start a program`
   - **Program/script:** `G:\unit3d\scripts\sync-daily.bat`
   - **Start in (optional):** `G:\unit3d`   ← **בלי** `\scripts`
   - **OK**
6. **OK** לסגירת החלון. ייתכן שיבקש את סיסמת המשתמש של Windows — זה תקין
   ונדרש בגלל האפשרות שסימנו בסעיף 3.

> ### השדה היחיד שאנשים מפספסים
>
> **"Start in"**, בסעיף 5. הוא מסומן "optional" ולכן קל לדלג עליו — אבל
> בלעדיו המשימה רצה מתיקייה אחרת, לא מוצאת את הפרויקט, **ונכשלת בשקט**.
> בלי הודעת שגיאה, בלי כלום. אם משהו לא עובד, תתחיל מלבדוק אותו.
>
> שים לב גם שהוא `G:\unit3d` ולא `G:\unit3d\scripts` — שונה מהשדה שמעליו.

### ✅ בדיקה — האם שלב 5 הצליח

## כשמשהו לא עובד

לבדוק לפי הסדר הזה. הראשון שנותן תשובה הוא הבעיה.

### 1. `G:\unit3d\scripts\sync-daily.log`

**הקובץ הראשון שפותחים, תמיד.** מה שהריצה האחרונה אמרה, בשורה האחרונה.

| מה כתוב בסוף | המשמעות |
|---|---|
| `pushed` | עבד, ויש מודלים חדשים ב-`/admin` |
| `nothing new` | עבד, פשוט לא נוסף כלום לאוספים |
| `TYPE CHECK FAILED` | הסנכרון מצא בעיה בקוד ועצר בכוונה — תגיד לי |
| `'git' is not recognized` | חזרה לשלב 1, תקלה ג |
| הקובץ ריק או לא קיים | **המשימה לא רצה בכלל** → סעיף 3 למטה |

### 2. `G:\unit3d\data\collections-status.json`

מה הריצה **ראתה**: אילו אוספים נקראו, כמה מודלים היו בכל אחד, ומה נחסם.

אם כתוב שם **`"signedIn": false`** — הפרופיל התנתק ממייקרוורלד.
להריץ שוב את `scripts\mw-login.bat`. **זה כל התיקון**, וזה לוקח דקה.

### 3. היומן ריק — המשימה לא רצה

ב-Task Scheduler, לסמן את המשימה ולפתוח את לשונית **History** למטה.

| מה רואים | התיקון |
|---|---|
| אין שורות בכלל | המשימה מושבתת — הקלקה ימנית ← **Enable** |
| שורות עם שגיאה | לבדוק את השדה **Start in** משלב 5 |
| "The task did not run because..." | המחשב היה כבוי ב-07:45 — בלשונית Settings לסמן ✅ *Run task as soon as possible after a scheduled start is missed* |

### 4. המחשב היה כבוי

הסנכרון רץ על המחשב שלך, אז הוא צריך שהמחשב יהיה דלוק ב-07:45. אם הוא
כבוי — הריצה פשוט מדלגת על אותו יום. שום דבר לא אבד; המודלים ימתינו
באוסף וייקלטו בריצה הבאה.

הסעיף האחרון בטבלה למעלה גורם לו להשלים את הריצה ברגע שהמחשב נדלק.
